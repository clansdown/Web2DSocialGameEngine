# Database architecture (PostgreSQL)

Ravenest uses **one PostgreSQL cluster with four independent logical databases**. There are no joins, foreign keys, or transactions across databases.

| Database | Purpose | URL variable |
|---|---|---|
| `ravenest_game` | accounts, sessions, characters, fiefdoms, retinue, combat, progression | `RAVENEST_GAME_DB_URL` |
| `ravenest_chat` | chats, messages, translations, social graph, moderation, push | `RAVENEST_CHAT_DB_URL` |
| `ravenest_staff` | staff roles, audit journal, support, notifications | `RAVENEST_STAFF_DB_URL` |
| `ravenest_invites` | invitation codes | `RAVENEST_INVITES_DB_URL` |

## Schema source of truth

The baseline DDL lives in:

```text
server/db/BaselineSchema.hpp
```

It is applied by `db::initialize_schema` (`server/db/Schema.cpp`) once per database and recorded in that database's `schema_migrations` table. The schema is idempotent (`CREATE TABLE IF NOT EXISTS`) and covers the complete pre-alpha baseline.

Per-table documentation remains under `server/tables/`. Treat those files as the human-readable schema reference; the DDL is authoritative for the runtime.

## Conventions

- IDs: `BIGINT GENERATED BY DEFAULT AS IDENTITY`
- Timestamps: `BIGINT` Unix seconds
- Booleans: integer `0`/`1` for compatibility with the existing game modules (`BOOLEAN` is used only for new chat translation eligibility)
- JSON payloads: `TEXT`
- Money: `DOUBLE PRECISION`
- Session ids: `UUID`
- Refresh token hashes: `TEXT` (SHA-256 hex)
- Case-insensitive uniqueness: `LOWER(...)` unique indexes
- `game_phase` is `TEXT` with no `CHECK`; validation lives in C++
- `stone` remains a column (retired; always 0) because the economy modules still read it

## Query adapter

The game has ~60 modules with embedded SQL. `server/db/postgres_sqlite_compat.hpp` provides the small `sqlite_modern_cpp`-style streaming API they already use, backed by libpq:

- one connection per thread per logical database
- `?` placeholders translated to native `$1`, `$2`, ...
- `INSERT OR IGNORE` → `ON CONFLICT DO NOTHING`
- `INSERT OR REPLACE` → `ON CONFLICT (<primary key>) DO UPDATE SET ...`
- `BEGIN IMMEDIATE` → `BEGIN`
- `last_insert_rowid()` / `SELECT last_insert_rowid()` → `LASTVAL()`
- a few legacy function translations (`instr`, `ifnull`, `group_concat`)

New code should use native PostgreSQL SQL with `$n` placeholders. The adapter exists so the rewrite can land as one PostgreSQL backend without a mixed SQLite/PostgreSQL runtime.

### Typed layer

`server/db/Database.hpp` defines the backend-neutral primitives:

- `db::value` (`monostate`/`int64_t`/`double`/`bool`/`string`/`blob`)
- `db::error` (`error_code`, SQLSTATE, message, retryable)
- `db::result` / `db::row`
- `db::connection_like` (compile-time concept; no virtual dispatch)
- `db::query_executor`
- `db::transaction` (RAII rollback)

`server/db/PostgresConnection.*` implements `connection_like` with libpq and
static-asserts the concept. `server/db/Executor.hpp` provides the bounded
per-database executor (`4` workers, queue `64`) and a four-database registry.
The existing game modules use the streaming adapter while they are migrated;
new repositories should target `db::connection_like` / `db::query_executor`.

## Transactions

- `db::initialize_schema` wraps the baseline in `BEGIN`/`COMMIT`.
- Game modules use `BEGIN`/`COMMIT`/`ROLLBACK` through the adapter.
- Read-modify-write paths that must be atomic use `SELECT ... FOR UPDATE` (session creation, invitation redemption).
- No transaction spans a network call.

## Session and invitation tables

`user_sessions` lives in `ravenest_game`. It holds one row per long-lived refresh session; access tokens are in memory only.

`invitation_codes` lives in `ravenest_invites`. Redemption is recorded twice:

1. `invitation_codes.used_at`/`used_by_account_id` (bookkeeping)
2. `users.invitation_code_id` with a partial unique index (the hard race guard)

## Migrations

- `0001` is the baseline in `BaselineSchema.hpp`.
- Future changes append a new numbered schema/runner step; do not edit an applied baseline in production.
- There is **no SQLite data migration**. Existing SQLite files are abandoned.

## Connection settings

The adapter applies per-connection:

```sql
SET statement_timeout = '5s';
SET lock_timeout = '2s';
SET idle_in_transaction_session_timeout = '10s';
```

`tools/init_postgres.sh` creates the role and four databases. See `docs/postgres_operations.md`.
